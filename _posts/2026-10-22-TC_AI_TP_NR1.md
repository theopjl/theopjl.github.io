#### Rappel sur la quantization

**Définition :** la quantization consiste à réduire la précision numérique des poids d'un modèle (et parfois des activations) pour diminuer son empreinte mémoire et accélérer l'inférence, au prix d'une perte de qualité plus ou moins marquée.

Un modèle est un ensemble de milliards de paramètres (les poids). Chaque poids est stocké sur un certain nombre de bits. Moins il y a de bits, moins le modèle pèse.

##### Ordre de grandeur de la mémoire

Taille approximative des poids = nombre de paramètres × bits par poids ÷ 8

| Format      | Bits par poids       | Taille d'un modèle 7B | Usage typique                         |
| ----------- | -------------------- | --------------------- | ------------------------------------- |
| FP16 / BF16 | 16                   | ~14 Go                | Entraînement, référence de qualité    |
| Q8_0        | 8 (~8,5 en pratique) | ~7,5 à 8 Go           | Qualité quasi identique à FP16        |
| Q4_K_M      | ~4,5 à 5             | ~4,4 à 4,7 Go         | Meilleur compromis taille / qualité   |
| Q2_K        | ~2,6 à 3             | ~2,5 à 3 Go           | Compression extrême, qualité dégradée |

📌 Les valeurs sont approximatives. Les formats K-quants stockent aussi des facteurs d'échelle par bloc, donc le nombre réel de bits par poids est supérieur au chiffre nominal.

##### Lire le nom d'une quantization (format GGUF)

Exemple : `Q4_K_M`

- **Q4** : environ 4 bits par poids.
- **K** : méthode « K-quants ». Les poids sont quantizés par blocs avec des facteurs d'échelle, ce qui préserve mieux la précision.
- **M** : variante Medium. `S` (Small) est plus compacte et moins précise, `L` (Large) est plus grosse et plus précise.
- **Q8_0** : 8 bits, méthode simple par blocs, sans variante K.

##### Ce que la quantization change (et ne change pas)

| Effet                                  | Explication                                                                                                                                                      |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ✅ Taille en mémoire                    | Elle diminue presque proportionnellement aux bits.                                                                                                               |
| ✅ Vitesse de génération                | La génération de tokens est limitée par la **bande passante mémoire** : à chaque token, tous les poids sont lus. Des poids plus légers donnent plus de tokens/s. |
| ✅ Tenue en VRAM                        | Un modèle plus léger peut rester à 100 % sur GPU.                                                                                                                |
| ⚠️ Qualité                              | Elle se dégrade lorsque la précision baisse, surtout sous 4 bits.                                                                                                |
| ⚠️ Ce n'est pas du nombre de paramètres | Quantizer un 32B ne le transforme pas en 7B. Il garde ses 32 milliards de paramètres, mais chacun est moins précis.                                              |

##### Ce qu'il faut garder en tête pour le TP

1. **Le nombre de paramètres et la précision des poids sont deux leviers distincts.** Le premier influence la capacité de raisonnement, le second l'empreinte mémoire et la fidélité.
2. **Au-dessus de 8 Go de VRAM, le modèle déborde sur la RAM** (offloading CPU). Les couches calculées par le CPU sont lues via la mémoire DDR, bien plus lente que la GDDR du GPU, et le débit s'effondre. Vous le verrez dans la colonne `PROCESSOR` de `ollama ps`.
3. **La VRAM ne contient pas que les poids.** Elle contient aussi le **KV cache** (qui grandit avec la longueur du contexte) et les buffers de calcul. Prévoyez une marge de 1 à 2 Go.
4. **La dégradation n'est pas linéaire.** Entre FP16 et Q8_0, la différence est quasi imperceptible. Entre Q8_0 et Q4_K_M, elle est généralement faible. En dessous (Q3, Q2), elle devient souvent nette : erreurs de logique, instructions mal suivies, code moins fiable.
5. **Tous les modèles `ollama pull` du catalogue officiel sont en Q4_K_M par défaut.** Sur HuggingFace, vous choisissez explicitement la quantization.

Le LLM devra trouver et corriger l'erreur, puis vous donner une analyse et justification.

##### Explication :

Plusieurs threads tentent d'accéder et de modifier une même variable simultanément.  Cette désynchronisation cause des valeurs inattendues. Pour résoudre cet accès concurrent (ou condition de course) il faut protéger la variable par un verrou (ou sémaphore) pour éviter qu'un autre thread ne change la valeur affectée à la variable pendant une modification. Le LLM devra être capable d'identifier la source du problème et la corriger. Tout en justifiant ces choix.

##### Le code érroné :

```python
import threading
import time

class Counter:
    def __init__(self):
        self.value = 0
        self.total_ops = 0
        self.history = []

    def increment(self, amount=1):
        current = self.value              # 1. lecture
        time.sleep(0)                     # 2. cède la main à un autre thread
        self.value = current + amount     # 3. écriture
        self.total_ops += 1
        self.history.append(self.value)

    def get(self):
        return self.value

def worker(counter, iterations):
    for _ in range(iterations):
        counter.increment()

def main():
    counter = Counter()
    n_threads, iterations = 8, 1000
    threads = [threading.Thread(target=worker, args=(counter, iterations))
               for _ in range(n_threads)]
    for t in threads:
        t.start()
    for t in threads:
        t.join()

    expected = n_threads * iterations
    print(f"Attendu   : {expected}")
    print(f"Obtenu    : {counter.get()}")
    print(f"total_ops : {counter.total_ops}")
    print("OK" if counter.get() == expected else "RACE CONDITION détectée")

if __name__ == "__main__":
    main()
```

import importlib.util
import sys

def run(path, runs=5):
    spec = importlib.util.spec_from_file_location("mod", path)
    mod = importlib.util.module_from_spec(spec)
    spec.loader.exec_module(mod)
    import threading
    ok = 0
    for _ in range(runs):
        c = mod.Counter()
        ts = [threading.Thread(target=mod.worker, args=(c, 1000)) for _ in range(8)]
        [t.start() for t in ts]
        [t.join() for t in ts]
        if c.get() == 8000 and c.total_ops == 8000 and len(c.history) == 8000:
            ok += 1
    print(f"{ok}/{runs} exécutions correctes")
    return ok == runs

if __name__ == "__main__":
    sys.exit(0 if run(sys.argv[1]) else 1)

##### ✍️ Comment lancer le test ?

1) Créer le fichier check_solution.py et y copier-coller le code de test ou récupérer le fichier sur MooTSE
```python
import importlib.util
import sys

def run(path, runs=5):
    spec = importlib.util.spec_from_file_location("mod", path)
    mod = importlib.util.module_from_spec(spec)
    spec.loader.exec_module(mod)
    import threading
    ok = 0
    for _ in range(runs):
        c = mod.Counter()
        ts = [threading.Thread(target=mod.worker, args=(c, 1000)) for _ in range(8)]
        [t.start() for t in ts]
        [t.join() for t in ts]
        if c.get() == 8000 and c.total_ops == 8000 and len(c.history) == 8000:
            ok += 1
    print(f"{ok}/{runs} exécutions correctes")
    return ok == runs

if __name__ == "__main__":
    sys.exit(0 if run(sys.argv[1]) else 1)
```
